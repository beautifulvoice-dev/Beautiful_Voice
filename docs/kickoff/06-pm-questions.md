## 🔴 화요일 전

> **답변 현황 (11/16):** ✅ Q1 확정(기기가 Wi-Fi로 직접 업로드). ✅ 웹 화면 방침 확정(기존 화면 미사용, UI/UX 새로 설계, 음성 시각 효과 불필요). 나머지는 회의 전 답변 대기.

**Q1. 마이크 기기는 어떻게 서버로 음성을 보내나요?** — ✅ **답변: (a) 기기가 Wi-Fi로 직접 업로드** (11/16)
- (a) 기기가 Wi-Fi로 직접 업로드 (b) 스마트폰과 블루투스 연결 후 폰이 업로드 (c) 녹음 후 USB/수동 업로드 (d) 미정
- 영향: (b)면 웹앱만으로는 어려워 **네이티브/하이브리드 앱이 필요**할 수 있음(현재 "네이티브 앱 초기 제외"와 충돌).
- 기본안: 기기 형태와 무관하게 **HTTPS 업로드 API**를 먼저 고정하고, 실물 전까지 샘플 파일 업로드로 개발.

**[확정] 웹 화면 방침** — 이전 프로젝트의 웹 화면은 쓰지 않는다. 가독성이 낮았고, 실시간 음성 대화용 시각 효과(voice orb)가 일방향 제품에서는 필요 없어졌다. **UI/UX는 새로 설계**한다(11/16).

**Q2. 원장님이 웹앱을 주로 어떤 기기로 보나요?** (스마트폰 / 태블릿 / 매장 PC)
- 기본안: 스마트폰 우선 반응형 웹(PWA, 홈 화면 추가).

**Q3. 같은 마이크로 "기록"과 "명령(조회·변경)"을 어떻게 구분하나요?**
- (a) 버튼/모드 분리 (b) 호출어("비서야, …") (c) AI가 자동 분류 후 웹앱에서 확인
- 기본안: (c) + 변경은 항상 승인을 거치므로 오분류 피해 제한. 단, 기기에 버튼 여유가 있으면 (a)가 정확도·비용 면에서 유리.

**Q5. 로그인·사용자 구조**
- 매장당 원장 1명만? 직원 계정이 있나요? 로그인 방식 선호(휴대폰 인증 / 카카오 / 이메일)?
- 기본안: 초기 매장당 원장 1명 + 휴대폰 번호 인증. 구조는 다중 사용자를 허용하게 설계.

**Q9. 개인정보·외부 AI 사용**
- 고객 음성·전사문을 **해외 AI 서비스(STT/LLM)로 보내도 되나요?** (국외 이전 고지·동의 필요 가능)
- 원본 음성 보관 기간? (예: 처리 후 30일 / 무기한)
- 기본안: 국내 리전 저장, 원본 음성 기본 90일 보관 후 삭제(설정 가능), 외부 API 사용은 파일럿 동의서에 포함.

## 🟠 스프린트 1 착수 전

**Q6. 예약 운영 규칙** (P2-03·04·11)
- 동시에 몇 명까지 받나요? (1인 = 동시 1명?) 시술 사이 준비 시간? 영업시간·휴무를 누가 입력?
- 충돌이 있어도 원장이 **강제로 저장**할 수 있어야 하나요?
- 예약 상태 목록: 요청 / 확정 / 취소 / 노쇼 / 완료 — 추가·삭제할 것?
- 기본안: 동시 1명, 준비 시간 메뉴별 설정, 강제 저장 불가(경고 후 시간 변경 유도), 상태는 위 5개.

**Q7. 관리 항목(메뉴) 목록과 소요 시간 데이터가 있나요?** 없으면 첫 화면에서 원장이 직접 입력하는 방식으로 진행.

**Q8. 고객 식별 필수 정보** — 이름만? 이름+전화번호 필수? (동명이인 구분 기준)
- 기본안: 이름 필수, 전화번호 권장(동명이인 시 필수).

**Q11. 음성/채팅으로 지원할 질문 Top 10** (P2-05·07의 "합의한 질문")
- 예: "오늘 예약 뭐 있어?", "김OO 고객 지난번에 뭐 받았지?", "다음 주 화요일 비는 시간?" — 실제 원장님 표현으로 받고 싶음.

**Q12. Phase 1을 카본 님이 직접 개발하시나요?** 그렇다면 같은 저장소·같은 데이터 모델·같은 PR 규칙으로 진행해도 될까요? (Phase 2 음성 기능이 Phase 1 파이프라인을 그대로 씀)

**Q13. 일정·예산**
- 8주의 시작일과 파일럿 매장 수·시점?
- 월 운영 예산 상한(호스팅 + STT/LLM)?
- 개발용 클라우드·AI API 계정은 누구 명의로 만드나요?

**S1 입력 요청:** 실제 매장 상황 발화 샘플 20~30개(가명 고객 사용) + 정답 문장. STT 벤더 비교에 필요.

**🔴 Q22. 코드 권리 관계** — 이전 코드 일부에 외부 조직 소유로 보이는 표기가 있습니다. 작은 유틸·스키마 패턴이라도 새 저장소에 옮겨도 되는지 확인 부탁드립니다. (확인 전에는 설계만 참고)

**🟠 Q15. 테스트셋 문제** — 이전 평가 세트에서 가장 컸던 문제가 무엇이었나요? 저희 분석으로는 ① 현실과 맞지 않는 무작위 메뉴·가격·소요 시간 ② 회차권을 1회 슬롯으로 처리 ③ LLM이 쓴 고객 발화 ④ 정답에 미확정 정책 포함. 새 테스트셋은 카본 님과 함께 설계하려 합니다.

**🟠 Q16. 한 녹음에 의도가 섞일 때** (Q3 보강) — "김OO 고객 오늘 관리 끝났고, 다음 주 화요일 3시 예약 잡아줘, 그리고 내일 예약 몇 개야?"처럼 기록+변경+조회가 섞이면 모두 처리할까요, 첫 의도만 처리하고 나머지는 확인 필요로 둘까요?
- 기본안: 모두 분리해 처리(기록은 저장, 조회는 결과 표시, 변경은 제안).

**🟠 Q17. 승인 부담** (Q4 보강) — 이전 실험에서 승인 단계가 많으면 쓰기가 끝까지 완료되지 않았습니다. 여러 제안 **일괄 승인**과, 미승인 제안 **자동 만료**(예: 24시간)를 허용할까요?

**🟠 Q18. 예약 운영 규칙 보강** (Q6) — 이전 코드에는 ① 겹침 예약을 원장 승인 시 허용 ② 시술 후 **정리 시간** ③ **임시 차단**(개인 일정) ④ 예약 시점 메뉴 정보 고정 저장이 있었습니다. 새 제품에도 넣을까요? 또 예약 상태에 "요청(접수)"을 두고, "완료"는 누가 표시하나요?

**🟠 Q19. 고객 필수 정보** (Q8 보강) — 이전 문서는 이름+전화+생년월일 필수, 코드는 이름+전화 필수였습니다. 원장님이 말로 남긴 메모나 장부에는 전화번호가 없는 경우가 많은데, 전화번호 없이 고객을 만들 수 있게 할까요?

**🟠 Q20. 원장 판단 영역** — 이전 제품은 의료 상담·환불·제3자 예약·마감 직전 변경을 "원장 판단"으로 넘겼습니다. 새 제품의 확인할 일(P1-07)과 전화 접수(P3-02)에도 같은 기준을 쓸까요?

**🟠 Q21. 지원 질문 1차 목록** (Q11 보강) — 이전 에이전트의 빠른 답변 4종(이름으로 고객 찾기 / 특정일 예약 수 / 빈 시간 / 다음 예약)을 1차 목록으로 써도 될까요? 추가할 질문이 있으면 알려 주세요.

**🟢 Q23. 날짜 표현 규칙** (P1-05) — "다음 주"는 월요일 시작? 이미 지난 "이번 주 금요일"은 다음 주 금요일로 볼까요, 확인 필요로 둘까요?
