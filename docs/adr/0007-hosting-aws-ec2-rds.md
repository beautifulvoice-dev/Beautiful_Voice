# 0007. 호스팅 — AWS EC2 + RDS PostgreSQL로 시작

- 상태: **Accepted** (2026-11-18 개발 리더 결정, Slack #소셜 "2A CRM 개발 환경 및 레포 운영 정리". 기록: 옵마)
- 날짜: 2026-11-18
- 결정자: 주드(개발 리더) — 05 R&R상 CI/CD·환경 책임
- 관련: D-08, Q9·Q13, F-08(시연 배포), [ADR-0001](0001-modular-monolith-single-postgres.md), [ADR-0006](0006-tech-stack-ts-monorepo.md), [02 §5](../kickoff/02-architecture.md)

## 맥락
ADR-0006은 호스팅을 Q13(예산·계정) 이후로 미뤘다. 11/17 회의에서 클라우드 비용은 팀 균등 분담·무료 티어 우선, 클라우드 계정은 리더 명의(Q13 답변)로 정리됐고, 1차 스프린트 2A는 팀 통합 테스트와 시연 환경이 필요하다.
제약: 고객 개인정보를 다루므로 저장은 국내 리전 우선(02 §5, D-08), PostgreSQL 배타 제약·RLS를 그대로 써야 한다(ADR-0003, C-05), API·워커 두 프로세스(ADR-0001).

## 고려한 선택지
1. **AWS EC2 + RDS PostgreSQL** — 표준 PostgreSQL 그대로(배타 제약·RLS·`btree_gist`), API·워커 프로세스를 자유롭게 띄움, 서울 리전·S3(음성 원본) 확장 가능. 단점: 서버·배포·HTTPS를 직접 구성.
2. 관리형 PaaS(Vercel + Supabase, Phase 1 방식) — 배포·인증 즉시 사용. 단점: 장시간 워커는 별도, 업체 종속, ADR-0006 구성(NestJS 워커)과 어긋남.
3. 국내 클라우드(NCP 등) — 국내 저장 명확. 단점: 팀 경험·무료 티어·레퍼런스가 적음.

## 결정
1번. 리더가 EC2와 RDS PostgreSQL을 생성했다(11/18).
- 2A: EC2(앱) + RDS PostgreSQL로 팀 통합 테스트·시연.
- 남은 구성: 앱 배포, 앱 전용 DB 권한(superuser·BYPASSRLS 금지 — ADR-0003), HTTPS 연결.
- 이후 확장(리더 계획): 음성은 Phase 1 저장소 재사용 여부를 먼저 보고, AWS에서 받게 되면 비공개 S3에 원본·RDS에 메타데이터. 오래 걸리는 처리는 백그라운드 워커 → 필요 시 큐. 외부 시연·파일럿 시점에 도메인·HTTPS·배포·오류 로그 절차.
- 새 자원 추가 시 필요 기능, 기존 자원 재사용, 예상 비용, 접근 권한을 확인하고 이슈나 ADR에 남긴다.

## 결과
- 좋아지는 점: 로컬(Docker Compose PostgreSQL)과 같은 표준 PostgreSQL이라 C-05 배타 제약·RLS가 그대로 동작. 워커 구조 제약이 없다.
- 감수하는 점: 배포·HTTPS·백업·보안 그룹을 팀이 직접 관리. 무료 티어 한도를 넘으면 비용 발생(팀 균등 분담).
- 되돌리는 비용: 중간 — 앱은 컨테이너·환경 변수로 옮길 수 있게 유지하면 낮다. DB는 표준 PostgreSQL이라 덤프로 이전 가능.
- 재검토 조건: ① 무료 티어 종료·비용 초과 ② 파일럿 개인정보 요구(국내 저장·접근 통제)를 만족하지 못할 때 ③ 운영 부담이 개발 일정을 잠식할 때.
