# 0002. AI의 데이터 변경은 ActionProposal → 승인 → 실행으로만

- 상태: **Accepted, 2026-11-26 개정** — 위험 단계(Tier)별 반영으로 바꿈(맨 아래 "2026-11-26 개정"이 현재 기준). 2026-11-19 개정(영역별 자동 모드)은 이 개정으로 대체. 처음 근거는 2026-11-18 PM 명세「[P2] 2. 상세 기능 명세서」A-1 "AI가 하는 모든 변경은 변경안 → 원장 승인 → 실행"
- 날짜: 2026-11-15
- 관련: PM 원칙 1·2, P2-06, P2-09, P3-05~07

## 맥락
PM 원칙상 기록·제안·승인·확정을 구분하고, 초기 AI 변경은 원장 확인 후 실행한다. 같은 요구가 P2-06(음성 변경), P2-09(장부 확정), Phase 3B(승인 후 처리)에서 반복된다.

## 고려한 선택지
1. **공통 `action_proposal` 엔티티 + 공통 승인 UI + 실행기** — 한 번 만들고 Phase 3B까지 재사용.
2. 기능마다 별도 확인 흐름 — 초기 구현은 빠르나 규칙·UI가 3벌로 갈라짐.

## 결정
1번. 제안은 변경 전/후 값·대상·근거(source_ref)·멱등키·만료 시각을 가진다. 실행기는 승인 시점에 대상의 최신 상태와 충돌을 재검사하고, 달라졌으면 재확인 상태로 돌린다.

보강(11/15, 이전 프로젝트 분석 반영):
- ~~**AI 출처 요청은 설정·모드와 무관하게 항상 제안**이다.~~ (→ 2026-11-19 개정으로 대체: 원장이 `auto`로 바꾼 영역은 예외) 이전 프로젝트는 "즉시 실행 가능" 목록을 두어 다수의 쓰기가 승인 없이 실행됐다.
- 제안은 **제안 시점 레코드 버전과 원장이 본 미리보기 해시**에 묶인다. 승인 시 버전이 달라졌으면 실행하지 않고 재확인한다.
- **승인 재사용 금지**, 같은 대상에 대한 정정 요청은 기존 제안을 `superseded`로 바꾸고 새 제안을 만든다.
- 실행 결과가 불명(타임아웃 등)이면 재시도 전에 상태를 조회한다.
- 승인 여부는 웹앱 탭으로만 받는다. 모델이 대화 내용을 승인으로 해석하지 않는다.

## 결과
- 좋아지는 점: AI 오류의 피해가 "잘못된 제안"으로 제한됨. Phase 3B 비용 감소.
- 감수하는 점: 단순 변경도 승인 단계를 거침(UX는 PM과 조율, Q4).
- 재검토 조건: ~~Phase 3C(조건부 자동) 착수 시 자동 승인 정책 추가~~ → 영역별 자동 반영은 3C와 별개로 Phase 2 M5(2B-4)에 들어온다(2026-11-19 개정). 전화 접수의 조건부 자동 확정(Phase 3)은 그때 다시 본다.

## 2026-11-19 개정 — 영역별 자동 모드 예외

> **2026-11-26 개정으로 대체됨.** 영역별 `manual`/`auto` 모드는 Tier 단계로 바뀌었다. 아래 "그대로인 것" 중 4(같은 쓰기 함수)·5(변경 이력·멱등)와 "AI는 설정을 바꾸지 못한다"는 새 개정에서도 유지된다.

**맥락.** 11/19 Phase 2 명세 최종판(Linear「[P2] 명세 1」§1.2·§1.3, 결정 R4·R24·R28·R32·R44)이 매장마다 영역(예약·고객·지갑·발송)별 모드 `manual`/`auto`를 정했다. `auto` 영역의 AI 업무는 승인 없이 바로 반영되고, 원장은 나중에 검수하거나 되돌린다. 명세는 이것이 이 ADR의 예외임을 밝히고 개발팀 기록을 후속으로 남겼다. 위 보강의 "AI 출처 요청은 설정·모드와 무관하게 항상 제안"은 **이 개정으로 대체한다**(PM 결정이 우선 — CLAUDE.md 절대 규칙 2).

**바뀌는 것**
- 업무 단위는 녹음이 아니라 업무(`crm_task`) 한 건이다. 이 ADR의 `action_proposal`은 `crm_task`로 구현한다(명세 2 §2.5).
- `manual` 영역: 지금과 같다 — 승인 대기 → 원장 승인 → 반영.
- `auto` 영역: 반영 → **검수 대기** 표시 → 원장이 검수 완료 또는 되돌리기. 수동 승인으로 반영된 업무에는 되돌리기가 없다.

**그대로인 것(자동 모드에서도 지킨다)**
1. 새 매장은 네 영역 모두 `manual`로 시작한다. 모드는 원장이 설정 화면에서만 바꾸고 **AI는 모드·설정을 바꾸지 못한다**. DB 권한으로도 막는다 — BEA-156(2F 권한과 역할별 접속)의 완료 조건 "AI 실행기의 설정 쓰기 거부".
2. **승인 필요 플래그**는 생성 시 모드가 `manual`이면 세우고, `auto→manual` 전환 때 미반영 업무에 세운다. 한 번 서면 풀리지 않는다. 자동 반영은 플래그가 없고 **설정 행을 잠근 상태에서 현재 모드가 `auto`일 때만** 한다.
3. 대상이 모호하면(고객 후보 여럿, 담당자 불명 등) 모드와 무관하게 **확인 대기**이고 아무것도 바꾸지 않는다.
4. AI 업무의 반영도 손 입력과 **같은 CRM 쓰기 함수·같은 검사**(겹침·차단·영업시간·version)를 지난다(절대 규칙 4). AI가 DB를 직접 쓰는 경로는 없다.
5. 반영·되돌리기는 변경 이력(`crm_change`)에 `actor_type=ai_task`와 업무 id(`source_task_id`)로 남는다. 같은 업무는 한 번만 반영한다(멱등).
6. 승인 여부는 웹앱 동작으로만 받는다. 모델이 대화 내용을 승인으로 해석하지 않는다.

**적용 시점.** 자동 반영은 M5(2B-4 자동 모드·되돌리기)에서 붙는다. 그 전까지 영역 모드 화면(2A-1)에서 `auto`는 고를 수 없고, 모든 AI 업무는 승인을 거친다.

**결과.** 좋아지는 점: 믿을 만한 영역은 말하자마자 반영돼 원장의 승인 부담이 준다. 감수하는 점: 자동 영역의 오류는 반영된 뒤에 발견되므로 검수·되돌리기·감독(2P-2)이 안전장치다. 재검토 조건: 자동 영역의 되돌리기·감독 오류율이 높으면 영역별 기본값과 플래그 정책을 다시 본다.

## 2026-11-26 개정 — 위험 단계(Tier)별 반영: 바로 반영 + 되돌리기

**맥락.** 2026-11-25 PM 전달 rev.3.1 명세(§8.1·§8.3, 수용 기준 AC-MS-18·19·22·42·48)가 AI 변경을 영역 모드가 아니라 **위험 단계(Tier 0~3)** 로 나눴다. 겹치지 않는 예약·메모처럼 되돌리기 쉬운 변경은 **승인 없이 바로 반영하고 되돌리기**로 관리하고, 돈과 문자는 지금처럼 **항상 원장 승인**을 거친다. PM 결정이 우선이므로(CLAUDE.md 절대 규칙 2) 이 ADR의 기본값을 바꾼다. 영역별 자동 모드(2026-11-19 개정)와 "M5 전까지 auto 불가"는 이 개정으로 대체한다.

**결정 — 단계별 처리**

| 단계 | AI 의도 | 처리 |
|---|---|---|
| Tier 0 | 조회(고객·예약·빈 시간·카드) | 바로. 상태 변경 없음 |
| Tier 1 | 겹치지 않는 미래 예약 생성·수정, 일정 차단 생성·수정·해제, 고객 기록 추가, 보조 정보(생년월일·동네) 수정, 직전 자동 반영 되돌리기 | **바로 반영 + 되돌리기** |
| Tier 2 | 모호함(동명이인·담당자·오전/오후), 누락 정보, 시간 겹침, 지난·진행 중 시각 예약, 예약 취소·노쇼, 고객 숨김 | **확인 카드** — 원장이 고르거나 채운 뒤 반영 |
| Tier 3 | 지갑 거래·횟수권 제안, 완료 처리, 모든 문자 | **승인 카드** — 원장 승인 후에만 실행 |

**Tier 1도 확인 카드로 바꾸는 경우** — 아래 중 하나면 바로 반영하지 않는다.
- 매장 설정에서 원장이 즉시 반영을 끔(기본 켜짐)
- 음성 인식 신뢰도가 기준 미만이거나 없음(웹 키보드 입력은 해당 없음)
- 녹음이 10분 넘게 늦게 도착, 기기 시계 미동기화, 미래 시각 오차 초과
- 그 매장의 유효한 원장 세션이 0건인 상태에서 도착한 와이파이·SD 녹음

**그대로인 것**
1. **AI가 DB를 직접 쓰는 경로는 없다.** 바로 반영도 손 입력과 **같은 도메인 쓰기 함수·같은 검사**(매장 격리·version·겹침 판정 등)를 지난다(절대 규칙 4). 바뀌는 것은 "언제 반영하나(승인 후 → 단계에 따라 바로)"이고 "어떻게 반영하나"는 같다.
2. **AI는 매장 설정·휴무·메뉴·담당자·문자 템플릿을 바꾸지 못하고**, 기존 지갑 거래를 고치거나 지우지 못한다(새 거래 제안만). DB 권한으로도 막는다.
3. 모든 반영·되돌리기는 행동 로그에 행위자(`ai_agent`)·원인·변경 전후와 함께 남고, 같은 요청은 한 번만 반영한다(멱등).
4. 대상이 모호하면 아무것도 바꾸지 않고 확인 카드로 간다.
5. Phase 2에서 AI는 문자 본문을 쓰지 않는다(등록된 템플릿만 고름). 승인 없는 문자 발송 경로는 없다.

**되돌리기**
- 바로 반영할 때 변경 전 상태(스냅샷)를 남기고, 원장이 되돌리면 그 상태로 돌린다. 예약을 되돌리면 연결된 사전 안내 문자 예약도 함께 취소한다.
- AI가 만든·바꾼 예약의 사전 안내 문자는 되돌릴 시간을 주도록 늦춰 보낸다(명세 §7.3).
- 그 뒤 같은 대상이 다시 바뀌었으면 되돌리기를 막는다(`UNDO_BLOCKED`). 고객 병합처럼 구조를 바꾸는 변경은 되돌리기 대상이 아니다.

**승인을 받는 방법도 바뀐다.** 위 보강의 "승인은 웹앱 탭으로만, 모델이 대화 내용을 승인으로 해석하지 않는다"를 바꾼다. 원장이 말로 승인하는 **원샷 음성 승인**(단건·일괄)을 허용하되, 승인 여부는 모델이 아니라 **서버 코드가 결정론적으로 판정**한다 — 같은 명령에서 만든 카드는 같은 명령으로 승인 불가, 다른 변경과 섞이면 승인 폐기, 명시적 승인 어휘 필수·부정어 차단, 위 "확인 카드로 바꾸는 경우"면 승인 의도 폐기. 고객 숨김은 터치로만 승인한다.

**적용 시점.** AI 에이전트는 Sprint 2(2026-12-02~)부터 구현한다. Sprint 1(웹 CRM)에는 AI 쓰기 경로가 없지만, 되돌리기 스냅샷·행동 로그·카드 모델은 Sprint 1 설계에서 이 개정을 전제로 한다.

**결과.** 좋아지는 점: 자주 하는 예약·메모가 말하자마자 끝나 원장 부담이 크게 준다. 감수하는 점: Tier 1 오류는 반영된 뒤 발견되므로 되돌리기·행동 로그·확인 카드 전환 조건이 안전장치이고, 이것들의 테스트가 필수다(절대 규칙 10). 재검토 조건: Tier 1 되돌리기 비율이 높거나 오반영 사고가 나면 Tier 1 범위와 기본값(즉시 반영 켜짐)을 다시 본다.
