# 0002. AI의 데이터 변경은 ActionProposal → 승인 → 실행으로만

- 상태: **Accepted, 2026-11-19 개정** — 영역별 자동 모드 예외 추가(아래 "2026-11-19 개정"). 처음 근거는 2026-11-18 PM 명세「[P2] 2. 상세 기능 명세서」A-1 "AI가 하는 모든 변경은 변경안 → 원장 승인 → 실행"
- 날짜: 2026-11-15
- 관련: PM 원칙 1·2, P2-06, P2-09, P3-05~07

## 맥락
PM 원칙상 기록·제안·승인·확정을 구분하고, 초기 AI 변경은 원장 확인 후 실행한다. 같은 요구가 P2-06(음성 변경), P2-09(장부 확정), Phase 3B(승인 후 처리)에서 반복된다.

## 고려한 선택지
1. **공통 `action_proposal` 엔티티 + 공통 승인 UI + 실행기** — 한 번 만들고 Phase 3B까지 재사용.
2. 기능마다 별도 확인 흐름 — 초기 구현은 빠르나 규칙·UI가 3벌로 갈라짐.

## 결정
1번. 제안은 변경 전/후 값·대상·근거(source_ref)·멱등키·만료 시각을 가진다. 실행기는 승인 시점에 대상의 최신 상태와 충돌을 재검사하고, 달라졌으면 재확인 상태로 돌린다.

보강(11/15, 이전 프로젝트 분석 반영):
- ~~**AI 출처 요청은 설정·모드와 무관하게 항상 제안**이다.~~ (→ 2026-11-19 개정으로 대체: 원장이 `auto`로 바꾼 영역은 예외) 이전 프로젝트는 "즉시 실행 가능" 목록을 두어 다수의 쓰기가 승인 없이 실행됐다.
- 제안은 **제안 시점 레코드 버전과 원장이 본 미리보기 해시**에 묶인다. 승인 시 버전이 달라졌으면 실행하지 않고 재확인한다.
- **승인 재사용 금지**, 같은 대상에 대한 정정 요청은 기존 제안을 `superseded`로 바꾸고 새 제안을 만든다.
- 실행 결과가 불명(타임아웃 등)이면 재시도 전에 상태를 조회한다.
- 승인 여부는 웹앱 탭으로만 받는다. 모델이 대화 내용을 승인으로 해석하지 않는다.

## 결과
- 좋아지는 점: AI 오류의 피해가 "잘못된 제안"으로 제한됨. Phase 3B 비용 감소.
- 감수하는 점: 단순 변경도 승인 단계를 거침(UX는 PM과 조율, Q4).
- 재검토 조건: ~~Phase 3C(조건부 자동) 착수 시 자동 승인 정책 추가~~ → 영역별 자동 반영은 3C와 별개로 Phase 2 M5(2B-4)에 들어온다(2026-11-19 개정). 전화 접수의 조건부 자동 확정(Phase 3)은 그때 다시 본다.

## 2026-11-19 개정 — 영역별 자동 모드 예외

**맥락.** 11/19 Phase 2 명세 최종판(Linear「[P2] 명세 1」§1.2·§1.3, 결정 R4·R24·R28·R32·R44)이 매장마다 영역(예약·고객·지갑·발송)별 모드 `manual`/`auto`를 정했다. `auto` 영역의 AI 업무는 승인 없이 바로 반영되고, 원장은 나중에 검수하거나 되돌린다. 명세는 이것이 이 ADR의 예외임을 밝히고 개발팀 기록을 후속으로 남겼다. 위 보강의 "AI 출처 요청은 설정·모드와 무관하게 항상 제안"은 **이 개정으로 대체한다**(PM 결정이 우선 — CLAUDE.md 절대 규칙 2).

**바뀌는 것**
- 업무 단위는 녹음이 아니라 업무(`crm_task`) 한 건이다. 이 ADR의 `action_proposal`은 `crm_task`로 구현한다(명세 2 §2.5).
- `manual` 영역: 지금과 같다 — 승인 대기 → 원장 승인 → 반영.
- `auto` 영역: 반영 → **검수 대기** 표시 → 원장이 검수 완료 또는 되돌리기. 수동 승인으로 반영된 업무에는 되돌리기가 없다.

**그대로인 것(자동 모드에서도 지킨다)**
1. 새 매장은 네 영역 모두 `manual`로 시작한다. 모드는 원장이 설정 화면에서만 바꾸고 **AI는 모드·설정을 바꾸지 못한다**. DB 권한으로도 막는다 — BEA-156(2F 권한과 역할별 접속)의 완료 조건 "AI 실행기의 설정 쓰기 거부".
2. **승인 필요 플래그**는 생성 시 모드가 `manual`이면 세우고, `auto→manual` 전환 때 미반영 업무에 세운다. 한 번 서면 풀리지 않는다. 자동 반영은 플래그가 없고 **설정 행을 잠근 상태에서 현재 모드가 `auto`일 때만** 한다.
3. 대상이 모호하면(고객 후보 여럿, 담당자 불명 등) 모드와 무관하게 **확인 대기**이고 아무것도 바꾸지 않는다.
4. AI 업무의 반영도 손 입력과 **같은 CRM 쓰기 함수·같은 검사**(겹침·차단·영업시간·version)를 지난다(절대 규칙 4). AI가 DB를 직접 쓰는 경로는 없다.
5. 반영·되돌리기는 변경 이력(`crm_change`)에 `actor_type=ai_task`와 업무 id(`source_task_id`)로 남는다. 같은 업무는 한 번만 반영한다(멱등).
6. 승인 여부는 웹앱 동작으로만 받는다. 모델이 대화 내용을 승인으로 해석하지 않는다.

**적용 시점.** 자동 반영은 M5(2B-4 자동 모드·되돌리기)에서 붙는다. 그 전까지 영역 모드 화면(2A-1)에서 `auto`는 고를 수 없고, 모든 AI 업무는 승인을 거친다.

**결과.** 좋아지는 점: 믿을 만한 영역은 말하자마자 반영돼 원장의 승인 부담이 준다. 감수하는 점: 자동 영역의 오류는 반영된 뒤에 발견되므로 검수·되돌리기·감독(2P-2)이 안전장치다. 재검토 조건: 자동 영역의 되돌리기·감독 오류율이 높으면 영역별 기본값과 플래그 정책을 다시 본다.
