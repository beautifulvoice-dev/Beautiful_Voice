# 0003. 테넌트 격리는 강제 RLS + 복합 FK + 역할 가드로

- 상태: **Proposed**
- 날짜: 2026-11-15
- 관련: COM-01, R5(개인정보), 이전 프로젝트 분석(02-architecture §7)

## 맥락
다른 매장의 고객·예약·녹음이 조회·변경되면 안 된다(COM-01). 애플리케이션 쿼리에 `shop_id` 조건을 빠뜨리는 실수는 AI 생성 코드에서 특히 흔하다. 이전 CRM 프로젝트는 PostgreSQL 강제 RLS와 매장 단위 복합 FK, RLS 우회 역할 거부 가드를 함께 써서 이 문제를 DB 수준에서 막았고, 분석 결과 이 부분은 품질이 좋았다.

## 고려한 선택지
1. **앱 레벨 필터만** — 단순하지만 누락 한 번이면 데이터 유출.
2. **강제 RLS + `(shop_id, id)` 복합 FK + 역할 가드** — DB가 최종 방어선. 세션마다 `app.shop_id` 설정 필요.
3. 매장별 스키마/DB 분리 — 격리는 확실하나 1인 샵 다수 운영·마이그레이션 비용이 큼.

## 결정 (제안)
2번.
- 모든 업무 테이블 `ENABLE` + `FORCE ROW LEVEL SECURITY`, 정책 `shop_id = current_setting('app.shop_id')::uuid`.
- 트랜잭션 시작 시 인증된 매장으로 `SET LOCAL app.shop_id`.
- 테이블 간 FK는 `(shop_id, id)` 복합 키.
- 앱 DB 역할은 superuser·`BYPASSRLS` 금지, 기동 시 검사해 위반이면 기동 거부. 마이그레이션 역할은 별도.
- 앱 레벨 `shop_id` 조건도 유지(이중 방어). 다른 매장 접근 거부 테스트를 계약 테스트에 포함.

## 결과
- 좋아지는 점: 쿼리 실수가 유출로 이어지지 않음. 파일럿 전 COM-01 검증이 쉬움.
- 감수하는 점: 커넥션 풀에서 세션 변수 관리 필요, 일부 ORM과 궁합 확인 필요.
- 되돌리는 비용: 낮음(정책 제거).
- 재검토 조건: 매장 수가 매우 커져 RLS 성능 문제가 측정될 때.
