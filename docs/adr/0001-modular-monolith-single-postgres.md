# 0001. 모듈형 모놀리스 + 단일 PostgreSQL

- 상태: **Accepted** (2026-11-17 킥오프에서 개발팀 합의 — 구체화는 [ADR-0006](0006-tech-stack-ts-monorepo.md), 구현 F-02 #22·F-03 #25)
- 날짜: 2026-11-15
- 관련: COM-01~03, P2-04, PM 원칙 3("같은 데이터와 예약 규칙"), 백로그 4.4

## 맥락
웹·음성·(향후)전화가 같은 고객·예약 데이터와 같은 예약 규칙을 써야 한다. 개발 인원 3~4명, 8주 목표. Phase 1·2가 각자 저장소를 만드는 방식은 PM 문서에서 배제됐다.

## 고려한 선택지
1. **모듈형 모놀리스(API 1 + Worker 1) + PostgreSQL 1개** — 규칙 공유 쉬움, 운영 단순. 모듈 경계는 코드 규율로 지켜야 함.
2. Phase/기능별 서비스 분리 — 독립 배포 가능하나, 예약 규칙·고객 데이터를 서비스 간 동기화해야 하고 3인 팀 운영 부담이 큼.
3. BaaS 중심 — 초기 속도는 빠르나 비동기 음성 처리에 별도 워커가 필요하고 벤더 종속.

## 결정 (제안)
1번. 음성 처리처럼 오래 걸리는 작업만 Worker로 분리하고, 큐는 초기엔 Postgres 기반으로 시작한다. 예약 충돌은 PostgreSQL 범위 타입·배타 제약으로 최종 보장한다.

## 결과
- 좋아지는 점: 모든 쓰기 경로가 같은 도메인 서비스·트랜잭션 사용, 충돌을 DB가 보장.
- 감수하는 점: 모듈 간 의존을 리뷰로 관리해야 함.
- 되돌리는 비용: 모듈 경계를 지키면 이후 분리 가능(중간).
- 재검토 조건: 전화(Phase 3) 실시간 처리 부하가 API와 분리돼야 할 때.
