# 0009. API의 매장은 주소가 아니라 로그인 세션으로 정한다 (앱 API부터, 웹은 뒤에 통일)

- 상태: Proposed (2026-11-26 옵마 결정 — 주드 확인 후 Accepted)
- 날짜: 2026-11-26
- 결정자: 옵마(제안·결정), 주드(리더 확인 대기)
- 관련: ADR-0003(매장 격리), ADR-0002 2026-11-26 개정, rev.3.1 명세 §3.1(1계정 = 1매장)·§3.4(세션)·데이터 계약 §3(모바일 API 계약, Sprint 1 동결), Sprint 1 작업 S10

## 맥락
지금 웹 API 32개는 매장을 주소에 넣는다(`/api/shops/{shopId}/…`). 세션의 매장과 주소의 매장이 다르면 404로 숨긴다(`OwnerShopGuard`). 매장 전환 가능성을 열어 두려고 이렇게 만들었다.

rev.3.1 명세는 **원장 계정 1개 = 매장 1개 고정**, 매장 전환 기능 없음으로 확정했다. 또 PM이 만든 안드로이드 앱(파일럿)은 이미 주소에 매장 없이 부르고(`/api/bootstrap`, `/api/actions/{id}/resolve`, `/api/ingest/audio` …), **로그인 토큰(Bearer)으로 매장을 정한다**. Sprint 1(12/01)에 이 모바일 API 계약을 동결해야 하고, 앱 개발은 PM 혼자 Sprint 2에 한다.

참고한 공개 API 방식: 토큰이 공간 하나에 묶이는 서비스(Slack·Notion·Linear)는 주소에 공간 ID를 넣지 않고, 한 사용자가 여러 조직을 오가는 서비스(GitHub `/orgs/{org}`, Google Cloud `projects/{id}`)는 주소에 넣는다. 어느 쪽이든 격리는 서버의 권한 확인이 지킨다.

## 고려한 선택지
1. **A→B: 앱용 새 API는 세션 기준, 기존 웹 API는 나중에 통일** — 앱 수정 없이 계약을 맞추고, 이번 스프린트에 기존 32개를 고치지 않는다. / 한동안 두 방식이 섞인다.
2. **C: 전부 주소 기준(지금 방식) 유지, 앱을 고침** — 우리 코드 변경 없음. / PM 앱 작업이 늘어 Sprint 2가 위험하고, 1계정=1매장에서 주소의 매장 ID는 쓸모없는 값이 된다.
3. **B를 지금 바로: 전부 세션 기준으로 한 번에** — 처음부터 하나로 깔끔하다. / 기존 API·웹 연결·테스트를 이번 스프린트에 다 고쳐야 해 시연 범위를 지키기 어렵다.

## 결정
1번(A→B).

- **A 단계(Sprint 1~2):** **새 리소스 묶음**(지갑·완료 카드·문자·템플릿·앱 API 등)은 주소에 매장을 넣지 않는다. 기존 리소스를 넓히는 일(고객 칸 추가·고객 하위 기록 등)은 B 단계 전까지 기존 주소를 따른다 — 한 리소스 안에서 두 방식이 섞이지 않게. 서버가 세션(웹 쿠키, 앱 Bearer 토큰)에서 매장을 정하고 매 요청마다 소속을 DB로 다시 확인한다. 앱이 부르는 주소·모양은 동결 계약(S10)대로 맞춘다. 세션 기준 가드와 웹 공용 경로 함수는 S1(계정·격리)에서 먼저 만든다.
- **B 단계(Sprint 2 이후 여유가 생길 때):** 기존 `/api/shops/{shopId}/…`를 세션 기준 주소로 옮긴다. 옮기는 동안 옛 주소는 같은 핸들러를 부르는 별칭으로 남기고, 웹 연결을 바꾼 뒤 지운다.
- **그대로인 것:** 격리는 ADR-0003(강제 RLS + 복합 FK + 역할 가드)이 지킨다. 서버는 요청 본문·주소로 들어온 고객·예약 등 ID가 세션 매장 소속인지 늘 다시 확인한다. 웹과 앱은 같은 도메인 서비스를 부른다(CLAUDE.md 절대 규칙 4).
- **다른 매장 리소스 접근:** 명세(AC-MS-02)대로 **403**. 기존 웹 API의 404 숨김은 B 단계에서 함께 맞춘다.
- 웹 쓰기 요청의 CSRF 대비(SameSite 쿠키 + `Idempotency-Key` 헤더, 동의 저장의 Origin 확인)는 그대로 둔다.

## 결과
- 좋아지는 점: PM 앱을 고치지 않고 Sprint 1 계약을 동결할 수 있다. 주소가 짧아지고 1계정=1매장 명세와 맞는다. 클라이언트가 매장 ID를 틀리게 보낼 여지가 없어진다.
- 감수하는 점: B 단계 전까지 웹 API에 두 방식이 섞인다. 웹 쿠키와 앱 토큰, 두 가지 인증을 함께 운영한다.
- 되돌리는 비용: A 단계는 낮다(새 API만 해당). B 단계 뒤 다시 주소 기준으로 돌아가려면 모든 주소를 바꿔야 해 높다.
- 재검토 조건: 한 원장이 여러 매장을 갖거나 운영자가 매장을 대신 다루는 기능이 생길 때(그때는 주소나 헤더로 매장을 지정하는 방식을 다시 본다).
